## Метод і межі доказів

Backend HEAD `f618bba290f919dc3561b0462c59b3b86ade82d8`, frontend HEAD `469d7e96abb0d90a80cdba377f83f8e6bb4a8081` перед змінами. Перелік отримано `php artisan route:list --path=api --json` (exit 0), зіставлено з `routes/api.php`; [точний знімок](evidence/api-routes.json). GET також приймає HEAD; це один route record. CSRF cookie, `/up`, framework routes та CLI scheduler не входять у 90.

Класифіковано **90/90**: **89 UI COVERED**, **1 PROGRAMMATICALLY COVERED**, **0 INTENTIONALLY NOT EXPOSED**, **0 MISSING FRONTEND INTEGRATION**, **0 NEEDS VERIFICATION** на рівні наявності клієнтського виклику. Це повний облік маршрутів, а не 100% відповідність вимогам чи live-verification кожного endpoint. Виявлені дефекти полів/стану G1–G3 наведено нижче.

`UI COVERED`: користувач відкриває сторінку, форму, фільтр або явно запускає дію; читання для відображення теж належить UI. `PROGRAMMATICALLY COVERED`: допоміжна перевірка доступу без окремої предметної операції. Немає невикористаних application API routes, які потрібно штучно виводити окремими кнопками. Наявність REST endpoint не означає доступ LLM.

Шляхи FE-тестів: `tests/` для `*.test.ts`, `e2e/` для `*.spec.ts`. BE-тести: `tests/Feature/` сусіднього backend, якщо не зазначено інше. Це посилання на **наявні релевантні assertions**, не твердження, що кожен test-file перевіряє кожен рядок. Поточні виконання та історичний CI відокремлено в [операційній перевірці](operational-verification.md). Основні клієнти знаходяться в `src/api/`, views у `src/views/`, reusable UI у `src/components/`; orchestration — у composables.

## Підтверджені UI-прогалини та результат

- **G1 — пагінація після lifecycle.** У pending/completed filter після зміни статусу останнього рядка на сторінці 2 сервер законно повертає empty page=2, last_page=1. Раніше UI приховував pager і залишав студента без попередніх записів. Додано reconciliation page за authoritative meta; так само обробляє видалення й зовнішнє зменшення списку. Два failing component regressions стали PASS.
- **G2 — неповний фільтр дедлайнів.** `ListTasksRequest` і `TaskFilters` підтримували deadline_from, але UI мав лише deadline_to. Додано нижню межу, timezone→UTC, просту UX-перевірку порядку та відображення backend validation messages через FormNotice. API/типи/серверний порядок не змінено.
- **G3 — повторне збереження Task.** Pending handler не мав guard, а після network/5xx можна було знову відправити create/update. Додано busy/uncertain guards у view і form; draft лишається на сторінці, mutation блокується, є явний link до списку для reconciliation. Це не новий серверний idempotency protocol. 422/419 лишаються відновлюваними; mutation не replay-иться автоматично.

Регресії: `tests/ui.test.ts` (6 нових cases), `e2e/tasks-coverage.spec.ts` (2 сценарії на кожний browser project). Поточні результати — в operational-verification. На початку G1–G3 класифіковано як дефекти workflow/field coverage вже інтегрованих routes; після виправлень route classification не змінюється.

## Решта видимих взаємодій

CRUD каталогів та дітей має confirm-delete/dirty-close; Task complete/reopen і незалежний progress не обіцяють завершення дітей або сесій. Lesson replacement/delete відновлює original за backend rules; date return враховує обидві дати. Import 409 змушує переглянути оновлений preview, lost response відновлюється читанням відомого Batch без auto-commit. Planning partial та unplaced-cancellation мають окремі unchecked згоди, stale/expired review не повторюється як нова mutation. Session cancel/reschedule показує наслідки; complete/miss умови перевіряє сервер. Reminder cancel зберігає історію, Inbox read не запускає dispatcher. AI confirm/reject/expired/failed/replayed показують authoritative state/receipt; frontend refresh не видається за нову mutation. Фільтри/діапазони, loading/error/empty та retry-read представлені у відповідних views.

Підтверджених кнопок-пустишок або route без користувацького entry point не виявлено. Відсутні формальні можливості (password, AI Lesson mutations, stats aggregates) не маскуються новими disabled кнопками; вони перелічені в requirements-coverage і потребують backend approval.
