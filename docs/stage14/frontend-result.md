# Stage 14B — Frontend: відновлення невиконаної роботи

## Результат і контракт

Реалізовано завершений потік `/planning/recovery` за наданим контрактом Backend Stage 14A
`f2c635744ad620eba5c2f032edea37e166c92089`. Backend source і GitHub не досліджувалися.

«Відновлення роботи» доступне з навігації та огляду планування. Сторінка повторно використовує
форму, пагінацію завдань, вибір підзавдання, перевірку дат, представлення плану та підтвердження
з `PlanPreviewView`. Окремого дубльованого потоку підтвердження чи HTTP-клієнта немає.

- `POST /api/planning/recovery/preview` надсилає дати й nullable `task_id` / `subtask_id`
  через наявний клієнт із Sanctum credentials і CSRF. Уся доступна робота охоплює також
  придатні завдання без пропущених сесій; остаточний відбір виконує Backend.
- Діагностика показує серверні кількості придатної роботи, пропусків і минулих запланованих
  сесій. Історія за всі дати відокремлена від періоду для нового плану. Є час, тривалість,
  посилання на роботу й сесію, українські пояснення причин і дозволених дій. Підзавдання
  відкриваються на наявній сторінці батьківського завдання.
- `requires_lifecycle_decision` показує видиме попередження, яке не блокує чинну пропозицію.
  Відновлення не змінює старі сесії, не виконує їхні lifecycle-дії та не скасовує нагадування.
  Воно розподіляє залишок роботи, а не замінює кожен пропуск один до одного.
- Для підтвердження використовується тільки `POST /api/planning/study-plans/confirm`
  із `preview_token` та `accept_partial`. Часткова пропозиція потребує явної згоди;
  adaptive-only згода на скасування не показується й не надсилається.
- Токен вилучається з даних відображення і залишається лише в тимчасовому стані компонента.
  Зміна періоду чи роботи, відхилення, вихід зі сторінки та недійсне підтвердження його скидають.
  Порожня пропозиція без токена й строку має окреме пояснення та не може бути підтверджена.
- Повторні натискання блокуються. Застарілі відповіді preview ігноруються після скасування.
  Підтвердження автоматично не повторюється. Після конфлікту, прострочення або втрати відповіді
  виконуються лише читання поточних даних; студент має зіставити сесії перед новим оглядом.
- Після успіху показано фактично збережені сесії з відповіді сервера, посилання на кожну та
  перехід до списку сесій. Помилка подальшого читання не перетворює збереження на невдачу.

## Перевірки

Під час реалізації пройшли 60 тестів `tests/planning.test.ts`, включно з 11 новими
recovery-випадками: preview/history, вибір роботи й скидання огляду, порожня відповідь без
токена, скасування застарілого preview, явна часткова згода, дублікати підтвердження,
повний план із advisory-попередженням, конфлікт 409, прострочення 422, втрачена відповідь
після фактичного збереження, помилки preview 404 і 500. Перевірено credentials/CSRF,
єдиний дозволений confirm endpoint, відсутність токена в HTML/URL/storage та незмінність історії.

Один наявний Playwright journey охоплює recovery preview, обидві групи історії, часткову
згоду, підтвердження та появу збереженої сесії в списку. Перевірено ширини 320, 768 і 1440 px
без горизонтального переповнення та автоматичний WCAG-аудит у світлій і темній темах.
Скриншоти генеруються лише як тестові артефакти; наявні зображення Docsify не змінювалися.

## Межі перевірки й Git

Автоматизовані перевірки використовують детерміновані HTTP-фікстури. Жива інтеграція з
Laravel/MySQL не виконувалася; реальна база та платні AI-операції не використовувалися.
Час розміщення, обсяг залишку, дозволені lifecycle-дії, доступність роботи, строк дії та
чинність підтвердження остаточно визначаються Backend. Невідомий код причини має загальне
українське пояснення з оригінальним кодом; його специфічний зміст потребує контракту сервера.
Нових залежностей, AI Tools або змін провайдерів Gemini/OpenAI немає.

Усі зміни виконано в `main`, без гілок, worktree, PR, reset, discard або push.

`883627953c0b28cea9fb152051f4eab0753fd2df`
(`feat(planning): add unfinished work recovery workflow`).
Наступний документаційний коміт фіксує лише цей звіт із результатами та SHA реалізації.
