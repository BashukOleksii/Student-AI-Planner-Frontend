# Чат: записи, читання й продовження розмови

2026-11-14. Перед змінами frontend і backend мали чисті робочі дерева; frontend
на main. Перевірено AGENTS.md, AiView.vue, AiComposer.vue, useAiConversation.ts,
API-клієнт та відновлення локального наміру. Backend-код не змінено.
Автоматизовані тести не додавалися, не редагувалися й не запускалися.

## Підтверджена причина

`AiView` блокує composer через `sending` або `decisionBusy`. Наявність pending
картки сама по собі не блокує composer. До виправлення `send()` очікував
`history()` та `loadActions()`, а останній також очікував `selectAction()`.
`decide()` утримував decisionBusy до завершення пов'язаних GET та історії.
Тому вже підтверджений запис міг лишати поле неактивним через повільне читання.

Це відтворено інтерактивно: після HTTP 200 підтвердження картка вже показувала
receipt виконаної дії, але з призупиненим GET історії `#ai-content.disabled=true`.
Другий запит у такому стані неможливо відправити з поля. Це frontend-блокування,
а не помилка другого POST від провайдера.

До старих карток можна повернутися зі списку дій та історії. Явні confirm/reject
виконувалися тільки натисканням відповідної кнопки.

Усі спостережені завершені POST запитів про дедлайни повернули 200, без
backend error code. Відтворені read failures та lost response — навмисна
браузерна імітація мережевої помилки, не 4xx/5xx від Gemini/Backend.
Підстав для зміни Backend не виявлено; конфігурацію провайдера не змінювали.

## Зміни та гарантії з коду

- sending та decisionBusy відпускаються після підтвердженої відповіді на запис.
  Follow-up GET запускаються незалежно й мають власні loading/error.
- Взаємні guards sending/decisionBusy не дозволяють паралельний send та decision.
  Preflight GET перед рішенням залишається: актуальний стан і огляд перевіряються
  перед POST; його помилка показується як помилка читання, а POST не виконується.
- Невідоме надсилання зберігає owner/conversation-scoped intent і ключ; явний retry
  використовує той самий ключ. Автоматичного resend/confirm немає.
- selectAction та domain reads перевіряють revision, ID і abort. Список дій
  враховує revision на початку send; пізній список не нав'язує іншу картку.
  Safe recovery рішення також використовує захищене читання деталей.
- Згода скидається для іншої картки, зміненого type/status/preview. Той самий
  незмінений огляд при повторному/фоновому GET не скидає consent. Для перевірених
  карток створення завдання немає окремих checkbox-згод, тому саме збереження
  заповнених checkbox оцінено з коду, а не заявляється як браузерний доказ.
- Нові сторінки історії об'єднуються за ID з уже прочитаними повідомленнями.
  Read error не стирає останні відомі дані й не перетворюється на send error.
- AiComposer перевірено: власного блокування за pending-карткою немає, його
  контракт не потребував зміни. Всі зміни зосереджені у composable та AiView.

## Межі висновків

Постійне блокування за самою наявністю непідтвердженої пропозиції не відтворено.
Підтверджена причина — write flags, що охоплювали наступні читання. Падіння
другого запиту в Backend для налаштованого провайдера не відтворено.
Клієнтські race guards і правила скидання consent додатково перевірено рев'ю коду;
ручна перевірка не є повним перебором мережевих перестановок.

Перевірки: TypeScript type-check, production build, Prettier змінених файлів,
git diff --check. Тестових команд не запускали.
