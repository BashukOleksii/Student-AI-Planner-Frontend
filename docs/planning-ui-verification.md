# Планування: результати перевірки UI

2026-11-14. Обидва репозиторії були чисті на main до змін.
Автоматизовані тести не додавалися, не редагувалися й не запускалися.

## Інтерактивно перевірено

Chrome через DevTools Protocol, з окремим локальним акаунтом перевірки
`auth-review-20261114-1949@example.test` (створений у попередньому завданні).
Дані для сценаріїв готували через локальний REST API. Штатний detector
`learning:detect-recovery --user=14 --days=7` запускали вручну для очікуваної
пропозиції; це не перевірка production-розкладу scheduler. Вкладку не перемикали.

- Вподобання: змінено ліміти й перерву, успіх залишає `/planning/preferences`,
  є «Вподобання збережено», дані й діагностика оновлені.
- Доступність: створено, змінено та видалено інтервал через UI; кожен успіх
  залишає `/planning/availability`, повідомлення й список відповідають дії.
- Після зміни вподобань відкрито пропозицію в тій самій вкладці: прочитано
  деталі та attention-status (`idle`, `check_pending=false`, `check_failed=false`).
  «Перевірити поточний стан» не потребує visibilitychange.
- Постійне блокування, яке зникає тільки після перемикання вкладки, **не
  відтворилося**. У фактично заблокованому огляді без заміни причина була
  відсутня окрема згода `accept_unplaced_cancellation`: тільки `accept_partial`
  недостатньо. Після обох згод кнопка активна. Повторне читання незміненого
  огляду залишило обидві згоди вибраними.
- Зміна вподобань після відкриття зробила той огляд `invalidated`: поточний
  стан показав застарівання, без переходу й без чекбоксів. Новий огляд отримав
  інший ID та обидві згоди false. Підтверджено окремою дією.
- Підтверджений успіх пропозиції, нового плану, ручного відновлення та
  standalone перепланування відкрив `/planning/sessions` із start_date/end_date
  й відповідним повідомленням role=status. Простий preview залишав свій маршрут.
- Для нового плану перед confirm вимкнено мережу: залишився `/planning/preview`,
  показано повідомлення зв'язку, старий confirm заблоковано. Після відновлення
  мережі новий preview та окремий confirm успішні; автоматичного повтору немає.
- Окрема заміна сесії: огляд інтервалу не переходить, підтвердження переносить
  на `/planning/sessions` із датою саме збереженої заміни та повідомленням.
- В історії застосованої пропозиції лишився результат, немає чекбоксів згоди
  та прибраної плашки. Для двох скасованих без заміни сесій показано
  «Було / Стало», початковий час і результат скасування. На 1366px — два блоки,
  на 390px — послідовні блоки, без горизонтального виходу.
- Огляд standalone перепланування: дві початкові сесії по 45 хв, кожна має
  два нові інтервали у своєму правому блоці; часткове перенесення залишає
  6 та 5 хв. Є окремі згоди на поділ і частковість. Успіх переводить до сесій.
- Навантаження: 90 хв роботи без доступності → справжні 0% з причинами;
  45 хв доступності на 90 хв роботи → 50%, 45 хв залишку;
  після розміщення всієї роботи → requested_seconds=0, нейтральне повідомлення,
  немає кільця/легенди/кнопки нового плану. Графік збережених 90 хв і виключена
  робота залишилися видимими.

## Висновки з коду, не окремі браузерні докази

- Раніше open читав тільки recoveryApi.get, а canConfirm також залежав від
  кешованого planningAttention. Його інтервальні/короткі читання могли скінчитися
  до завершення перевірки; visibilitychange відновлював читання. Це пояснює
  можливий стан, але не доводить причину конкретного попереднього випадку.
- Тепер відкриття й явна перевірка перечитують релевантний attention-status;
  pending/error/stale/uncertain/lifecycle/consent мають різні пояснення.
  Жоден guard серверного confirm не вимкнено. Фонова перевірка attention не
  обнуляє згоди; ID, review, статус, строк і набір вимог визначають нову згоду.
- Невідомий результат/конфлікт не викликають success-навігацію. Відхилення й
  оновлення пропозиції також лишають огляд. Поведінка підтверджень AI не змінена.
- Старі receipts можуть не містити початкового часу або replacement_groups.
  Нові результати додають початкові UTC-інтервали; старі лишаються читабельними
  з даними збереженого review або поясненням відсутності зв'язків, без їх вгадування.
- Full replacement, split, partial remainder, no replacement мають окремі
  пояснення. Обіцянка скасування без заміни стосується лише requires_replanning
  із released_session_ids. Ручні рішення не перетворені на автоматичні скасування.
- [Аудит виходу](planning-exit-dialog-audit.md) описує guards/close handlers усіх
  знайдених груп. Підтвердження незворотних дій та discard guards не видалялися;
  повний ручний обхід кожної форми аудиту не проводився.
