# Архітектура системи

[Зміст комплекту](README.md) · [Діаграми](diagrams/README.md) · [REST API](api-overview.md)

## Мета і межі

Student AI Planner допомагає студенту поєднати розклад занять, завдання, строки виконання та доступний час для самостійної роботи. Система зберігає академічний контекст, обчислює вільні інтервали, пропонує й після підтвердження зберігає навчальні сесії, підтримує перепланування, нагадування та статистику. AI-помічник додає природномовний доступ до контрольованих серверних можливостей.

Це два незалежні застосунки:

| Частина | Репозиторій                                                                                 | Відповідальність                                                             |
| ------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| SPA     | [Student-AI-Planner-Frontend](https://github.com/BashukOleksii/Student-AI-Planner-Frontend) | Взаємодія, форми, маршрути, огляд наслідків і явне підтвердження             |
| Сервер  | [Student-AI-Planner-Backend](https://github.com/BashukOleksii/Student-AI-Planner-Backend)   | REST API, автентифікація, права доступу, бізнес-правила, транзакції та MySQL |

Laravel — модульний моноліт: функціональні групи Services в одному серверному застосунку. Окремі розгортання SPA й API не роблять доменні модулі мікросервісами. Розподілені черги, брокери подій, окрема векторна БД чи власна навчена модель тут не реалізовані. Таблиці стандартної Laravel-черги існують, але AI-запит і локальна доставка нагадування в поточному коді не є фоновими queue Jobs.

## Клієнт

Фактичний стек: Vue 3, TypeScript, Vite, Vue Router, Pinia, Composition API та `<script setup lang="ts">`. Встановлені залежності зафіксовано lock-файлом; [package.json](../../package.json) визначає команди перевірки. Бібліотека `@js-temporal/polyfill` використовується для часових перетворень, Manrope — для шрифту.

| Шар                             | Фактичні файли/каталоги                                                                                                    | Роль                                                                                |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Маршрути                        | [src/router/index.ts](../../src/router/index.ts)                                                                           | Ліниве завантаження сторінок, перевірка сеансу, безпечний внутрішній redirect       |
| Сторінки                        | [src/views](../../src/views)                                                                                               | Оркестрація UI конкретного сценарію                                                 |

| Спільний стан                   | [auth.ts](../../src/stores/auth.ts), [theme.ts](../../src/stores/theme.ts)                                                 | Автентифікований профіль і тема; доменні дані не складено в один глобальний store   |

## Сервер

Залежності: PHP `^8.3`, Laravel `^13.17`, Sanctum `^4.0`, PhpSpreadsheet `^5.10`; це діапазони composer.json, а не заява про версії кожного середовища. У Stage 8 працювали Laravel 13.33.0, PHP 8.5.11 і MySQL 8.4.10; hosted backend CI використовує PHP 8.4/MySQL 8.4.

## Потік даних і автентифікація

Студент → Vue View → API-модуль → HTTP → Laravel middleware → Controller/Form Request/Policy → Service → Eloquent/MySQL → Resource → API-модуль → UI. Валідація, авторизація й route binding виконуються відповідно до Laravel lifecycle; це логічний опис шарів, а не універсальний порядок викликів для кожного endpoint.

Sanctum використовується в SPA cookie-режимі. Браузер отримує XSRF-cookie через `GET /sanctum/csrf-cookie`, а зміни надсилає з `credentials: include` та декодованим `X-XSRF-TOKEN`. Laravel створює/регенерує сеанс під час реєстрації та входу; вихід інвалідовує сеанс і регенерує CSRF-токен. Приватні маршрути захищено `auth:sanctum`; ID власника надходить із серверної автентифікації, не з аргументів користувача чи LLM.

`VITE_API_BASE_URL` задає публічну адресу API на етапі збирання. CORS дозволяє конкретний origin із credentials, Sanctum має узгоджені stateful hosts. Налаштування localhost не підтверджують поведінку HTTPS-проксі. Сесія не зберігається як bearer token у localStorage. Тема зберігається локально, а непідтверджений намір AI може зберігатися в owner-scoped sessionStorage для відновлення; це не автентифікаційні дані.

## Час, планування та узгодженість

У БД доменні DATETIME трактуються як UTC. Профіль містить IANA timezone; доступність — локальний день тижня і час. Діапазони задаються локальними календарними датами, до 31 включно. Інтервали обробляються як напіввідкриті `[start, end)`: дотик меж не дорівнює перетину. Неоднозначні/неіснуючі локальні моменти не можна мовчки вгадувати.

`FreeTimeService` віднімає активні Lessons і planned StudySessions від доступних вікон. Він не застосовує всі навчальні обмеження, тому наявність вільного часу не гарантує здійсненність плану. Повний план додатково перевіряє строки, залишок роботи, перерви, денні/тижневі ліміти й тривалість сесій. Докладний алгоритм наведено у [функціональному огляді](functional-overview.md#детермінований-алгоритм-планування).

Прямий preview не створює StudySessions. Підтвердження повторно обчислює матеріально той самий план під блокуванням власника, перевіряє згоду на частковий результат і зберігає весь пакет у транзакції. Короткоживучий захищений токен не є довговічною квитанцією. Для AI підтвердження додатково зберігаються статус дії та receipt у спільній транзакції. Статистика використовує узгоджене читання MySQL REPEATABLE READ, а не «історичну копію» всіх станів.

## Чому розрахунки не доручено LLM

Однакові дані й правила повинні давати відтворюваний результат, захищати власність і витримувати конкурентні зміни. Детерміновані Services мають явні типи, правила, транзакції та тести без провайдера. LLM обирає дозволені інструменти й уточнює намір; вона не встановлює повноваження, не підміняє перевірку конфліктів та не вигадує статистику. Це дозволяє перевіряти домен навіть без API-ключа OpenAI.

## Обробка помилок

[ApiError](../../src/api/client.ts) розрізняє мережеву помилку, 401/419, 403/404, 409/410, 422, 429 та серверні збої. UI показує безпечне пояснення й окремі помилки полів. На 401 стан автентифікації очищається; на 419 потрібне відновлення сеансу перед новою свідомою дією. Мутації не повторюються автоматично. Після втраченої відповіді імпорту/планування необхідно прочитати збережений стан; AI використовує свій підтверджений receipt/Idempotency-Key протокол. Сервер має окремі безпечні JSON-обробники для AI, планування, нагадувань і статистики; це не твердження про однаковий envelope усіх помилок.

## Рішення і компроміси

| Рішення                                         | Перевага                                                   | Обмеження                                                                |
| ----------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| Laravel-моноліт + незалежна SPA                 | Спільні Services, локальні транзакції, окреме збирання UI  | Потрібно узгоджувати API, CORS і cookie-конфігурацію                     |
| Cookie-сесія Sanctum                            | Серверний контроль сеансу, HttpOnly cookie                 | Залежність від CSRF, origin, SameSite і HTTPS-топології                  |
| Жадібний детермінований розподіл                | Пояснюваний порядок і точні причини неповного плану        | Немає доказу глобальної оптимальності чи покращення успішності студентів |
| Блокування власника перед доменними записами    | Послідовні перевірки пов'язаних даних                      | Записи одного студента можуть очікувати одне одного                      |
| Збереження історії сесій/м'яке видалення роботи | Аудит, зв'язок перенесень і статистика                     | Складніша перевірка історичних посилань                                  |
| AI як контрольований оркестратор                | Доступність природної мови без перенесення правил у модель | Залежність якості діалогу від провайдера; платна перевірка окрема        |
