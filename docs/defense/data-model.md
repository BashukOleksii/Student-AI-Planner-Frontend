# Модель даних і правила цілісності

[Зміст](README.md) · [ER-джерело](diagrams/data-model.mmd) · [Перегляд діаграми](diagrams/README.md#модель-даних)

Модель звірено з усіма **25 Laravel-міграціями**, поточними Eloquent-зв'язками й підсумковим станом Stage 8: **28 таблиць**, включно зі службовою `migrations`. Ця таблиця створюється механізмом Laravel `DatabaseMigrationRepository`, а не окремою міграцією застосунку. ER показує всі 28 таблиць і вибрані ключові поля; це не повний SQL DDL. Точні довжини, nullability, індекси та CHECK визначають [міграції Backend](https://github.com/BashukOleksii/Student-AI-Planner-Backend/tree/f618bba290f919dc3561b0462c59b3b86ade82d8/database/migrations).

## Службові таблиці

| Таблиця                  | Ключові поля                                                                                              | Межа функціонального висновку                                                                     |
| ------------------------ | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `sessions`               | string PK `id`, nullable indexed `user_id`, `ip_address`, `user_agent`, `payload`, `last_activity`        | У Stage 8 database session driver; **FK до users не оголошений**                                  |
| `password_reset_tokens`  | PK `email`, `token`, nullable `created_at`                                                                | Framework scaffolding; немає реалізованого public reset-потоку                                    |
| `personal_access_tokens` | `id`, `tokenable_type`, `tokenable_id`, `name`, unique `token`, `abilities`, `last_used_at`, `expires_at` | Sanctum-міграція; поточна SPA використовує cookie, а User не додає потік видачі bearer-токенів    |
| `cache`                  | PK `key`, `value`, `expiration`                                                                           | Laravel cache store                                                                               |
| `cache_locks`            | PK `key`, `owner`, `expiration`                                                                           | Блокування cache store; не заміна доменних SQL locks                                              |
| `jobs`                   | `id`, `queue`, `payload`, `attempts`, `reserved_at`, `available_at`, `created_at`                         | Стандартна інфраструктура черги; її наявність не означає фонове виконання AI чи Reminder delivery |
| `job_batches`            | string PK `id`, лічильники jobs, `failed_job_ids`, `options`, часові поля                                 | Інфраструктура пакетів Jobs                                                                       |
| `failed_jobs`            | `id`, unique `uuid`, `connection`, `queue`, `payload`, `exception`, `failed_at`                           | Облік невдалих Jobs                                                                               |
| `migrations`             | integer PK `id`, `migration`, `batch`                                                                     | Облік застосованих міграцій Laravel                                                               |

У більшості предметних таблиць є стандартні created_at/updated_at; у ai_messages використано лише created_at. ER навмисно не повторює всі службові timestamps. Поліморфні `notifications.notifiable_*` і `personal_access_tokens.tokenable_*` не є звичайними SQL FK. У ER logical morph Notification → User підписано явно; універсальний tokenable не прив'язано до вигаданої поточної token-функції User.

## Суттєві обмеження

- `planning_preferences.user_id` гарантує не більше одного набору налаштувань. FK видаляє його разом із власником.
- Nullable academic institution references використовують SET NULL; залежні Lessons/Batch можуть заборонити видалення AcademicPeriod. `lessons.subject_id` — обов'язковий FK із RESTRICT, `tasks.subject_id` — nullable із SET NULL.
- `lessons.replaces_lesson_id` і `study_sessions.rescheduled_from_session_id` — nullable UNIQUE: не більше одного безпосереднього наступника. Належність одному власнику, відповідність Task/Subtask і відсутність циклів контролюють Services, не сам FK.
- UNIQUE `(user_id, academic_period_id, import_fingerprint)` резервує імпортовану ідентичність Lesson. `deleted_at` не входить до ключа: історія не стає новим незалежним імпортом після м'якого видалення.
- Lessons, Tasks і Subtasks мають soft delete. StudySessions та Reminders зберігають історичні статуси; бізнес-видалення залежностей не слід підміняти фізичним CASCADE, доступним у схемі для адміністративного видалення.
- `notifications.reminder_id` nullable UNIQUE захищає один локальний receipt на Reminder; після можливого адміністративного видалення джерела SET NULL зберігає Inbox-історію.
- `ai_pending_actions.turn_id` UNIQUE забезпечує максимум одну збережену пропозицію на хід. Статус executed вимагає receipt і resolved_at; pending має незаданий resolved_at. Фінальні міграції розширили allowlist типів до всіх 14 пропозицій.
- Перевірки enum-подібних рядків, позитивної тривалості, priority, зв'язку completed/completed_at та sent/sent_at — фактичні MySQL CHECK. Повна власність, перетини, коректна одна ціль Reminder і міжрядкові доменні інваріанти залишаються відповідальністю Services/Policies.

## Час і відсутність зайвої персистенції

Доменні часові моменти зберігаються як UTC; timezone користувача — IANA-рядок, а availability — локальні TIME/day_of_week. Action/lease timestamps можуть мати мікросекунди. Публічні доменні інтервали переважно мають формат `YYYY-MM-DDTHH:mm:ssZ`; службові AI/as_of timestamps можуть містити дробову частину.

Окремих таблиць `free_slots`, `study_plans`, `statistics`, `reports` або `tool_executions` немає. Вільний час/плани/звіти обчислюються; підтверджений план персистує як `study_sessions`. Tool-події зберігаються у структурованій AI-історії, а виконана AI-дія — в `ai_pending_actions.receipt`.

Це розрізнення важливе для пояснення ER: назва екрану або класу Service не обов'язково є назвою таблиці.
