## Термінологія

| Термін у коді                         | Термін у поясненні                                                    |
| ------------------------------------- | --------------------------------------------------------------------- |
| EducationInstitution / AcademicPeriod | Заклад освіти / академічний період                                    |
| Subject / Teacher                     | Навчальна дисципліна / викладач                                       |
| Lesson                                | Заняття розкладу, обов'язкова зайнятість                              |
| Task / Subtask                        | Завдання / підзавдання                                                |
| StudySession                          | Навчальна сесія самостійної роботи над завданням                      |
| Reminder / Notification               | Нагадування як запланована умова / збережене сповіщення у Inbox       |
| Preview / confirmation / receipt      | Попередній огляд / явне підтвердження / збережена квитанція виконання |

Заклади, дисципліни й викладачі — персональні записи користувача, а не спільний університетський каталог. Lesson і StudySession мають різне призначення й окремі життєві цикли.

## Детермінований алгоритм планування

1. `PlanningWorkSelectionService` завантажує власні Tasks/Subtasks і пов'язані сесії. За наявності активних дітей вони є одиницями планування, щоб не рахувати обсяг батька вдруге. Завершені/непридатні одиниці виключаються з явними причинами.
2. `RemainingEffortService` переводить оцінку хвилин у секунди. Кредит завершеної сесії: `actual_minutes × 60`, якщо фактичні хвилини задані, інакше її запланована тривалість. `remaining = max(0, estimate − completed_credit)`, `unallocated = max(0, remaining − valid_future_reserved)`. Невідома оцінка лишається невідомою. Це планувальна облікова політика, а не підстановка вигаданих фактичних хвилин у статистику.
3. Порядок: наявність дедлайну, раніший ефективний дедлайн, вищий пріоритет, ID Task, позиція та ID Subtask. Ефективний строк дитини враховує батьківський строк.
4. `PlanningContextService` формує узгоджений контекст доступності, активних Lessons, planned Sessions, навчальних навантажень і перерв. Інтервали мають UTC-межі; календарні обмеження враховують timezone профілю.
5. `StudySessionAllocationService` послідовно шукає допустимі розміщення й ділить обсяг з урахуванням мінімальної/максимальної сесії, залишку до дедлайну, місткості дня/тижня й перерв. Після кожної пропозиції змінюється проєктований контекст наступних розміщень.
6. Результат містить sessions, work_results, excluded_items, warnings і summary з allocated/unscheduled seconds та fully_allocated. Непоміщений залишок не приховується. Це детермінована жадібна стратегія, а не доведений глобальний оптимум.
7. `StudyPlanPersistenceService` видає захищений preview token на 900 секунд. Confirm блокує власника, повторює розрахунок, звіряє матеріальний результат, перевіряє весь пакет і зберігає його атомарно. За зміни стану потрібен новий огляд, а не мовчки інший план.

## Перепланування та життєві цикли

`StudyReplanningPreviewService` і `StudyReplanningAnalysisService` аналізують фактичні джерела, розрізняючи valid, requires_replanning та cannot_replan. Придатні резервування зберігаються; уражені джерела можуть отримати одного наступника. `StudyReplanningPersistenceService` повторно перевіряє повний огляд і фіксує зміни, наступників та скасування старих запланованих нагадувань разом. Неперенесені джерела не можна скасувати без окремої згоди.

| Дія StudySession | Вихідний стан | Часова умова                                                      |
| ---------------- | ------------- | ----------------------------------------------------------------- |
| complete         | planned       | Початок уже настав; фактичні хвилини позитивні або null           |
| miss             | planned       | Кінець уже настав                                                 |
| cancel           | planned       | Початок ще в майбутньому                                          |
| reschedule       | planned       | Початок ще в майбутньому; наступник проходить актуальні перевірки |

У REST complete невідомі actual_minutes передаються відсутністю поля; явний null не проходить Form Request, хоча збережене значення залишається null. Не слід на захисті «завершувати» майбутню сесію чи змінювати системний годинник. Реальна Stage 8 перевірила майбутні reschedule/cancel; elapsed complete/miss лишилися окремими неперевіреними live-випадками.

## Імпорт, нагадування та статистика

XLSX імпорт складається з парсингу підтриманого шаблону, календарної матеріалізації для AcademicPeriod, прив'язування власних Subject/Teacher, класифікації операцій і збереження concrete preview. PhpSpreadsheet не використовується як довільний імпорт даних у таблиці MySQL. Файл перевіряється як `.xlsx` до 5120 КБ; формули не обчислюються парсером. Операції рядків: create, update, restore, preserve, noop. Перед commit сервер повторно звіряє preview: 409 може означати вже оновлений збережений огляд, але без застосування змін Lessons.

Відносний Reminder має один відповідний target, anchor і signed offset_minutes; trigger розраховує сервер. Нагадування та Inbox мають різні стани: scheduled → sent/cancelled і незалежний read_at у Notification. Хвилинний Laravel scheduler викликає існуючий диспетчер; він атомарно зберігає Notification і sent_at. У Stage 8 ця доставка не запускалась.

Статистика розділяє Tasks і Subtasks, поточні стани та завершення в періоді. Сесії атрибутуються за starts_at, враховуються п'ять статусів і заплановані секунди. Відомі фактичні хвилини сумуються окремо; невідомі рахуються окремим лічильником. Trends заповнює нульові дні; Comparison вимагає однаково довгі впорядковані неперетинні періоди й повертає signed delta. Немає експорту PDF/Excel-звітів, передбачення оцінок чи виміряного підвищення успішності.
