Це план майбутнього виступу. Часи — запланований бюджет, а не виміряна швидкість застосунку. Нові дані й показ paid-provider/dispatcher не створюються цим документом. До виступу оператор має погодити доступ і нові демонстраційні записи; Stage 8 fixtures зберігаються.

Перевірені функції та неперевірені зовнішні операції задокументовані окремо. Я не стверджую про доведений вплив на успішність студентів чи готове production-розгортання».

## Варіант на 10 хвилин

Залишити архітектуру й основний планувальний потік, а XLSX, replanning та Reminder показати через вже збережені результати без нових записів. Скоротити вступ до 25 секунд, академічний контекст до 35, Excel до 40, Task/Subtask до 45, free slots до 30, replanning до 45, Reminders до 35, статистику до 50, AI до 55 і висновок до 65 секунд; не прискорювати введення приватних даних у трансляції. Це приблизний сценарій репетиції, не гарантія тривалості мережевих операцій.

Не жертвувати поясненням меж довіри та різниці preview/commit заради показу всіх кнопок. Якщо відповідь затримується, перейти до збереженого доказу з чесною позначкою.

## Типові запитання комісії

| Запитання                                           | Стисла технічно точна відповідь                                                                                                                                                     |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Де саме AI?                                         | У Laravel AgentOrchestrator та LlmProvider: модель обирає фіксовані Tools; Services виконують розрахунки й перевірки.                                                               |
| Чому планує не LLM?                                 | План має бути відтворюваним, перевіреним щодо власності, часу й конкурентних змін. Ці гарантії забезпечує код із тестами.                                                           |
| Чи навчали власну модель?                           | Ні. Є адаптер OpenAI Responses API й серверна оркестрація; live paid-provider acceptance не проводилась.                                                                            |
| Чи все вже працює через реальний AI?                | Доменний REST і MySQL пройшли live; AI-контракти/confirmation покриті детермінованими тестами з підмінним провайдером. Реальну платну відповідь не видаємо за перевірену.           |
| Що станеться після двох натискань confirm?          | AI-дія має довговічний receipt і replayed. Прямий планувальний token має інший протокол: актуальність перевіряється повторно; невизначену зміну читають перед новим підтвердженням. |
| Чи «так» у чаті є дозволом?                         | Ні. Потрібен окремий автентифікований REST confirm із явними UI-згодами.                                                                                                            |
| Як захищені дані різних студентів?                  | Sanctum задає User; Policies, scoped relations і Services перевіряють власність. FK сам по собі не доводить, що пов'язані записи одного користувача.                                |
| Чому після Task complete лишилися planned Sessions? | Це незалежні lifecycle; Task completion синхронізує Reminders, але не завершує чи скасовує Sessions. Planning повертає відповідні діагностичні причини.                             |
| Чи нагадування доставлене?                          | У Stage 8 перевірено створення/синхронізацію, але dispatcher не запускався. Код локальної доставки та Inbox тестувався окремо на backend; live-доставка лишається gate.             |
| Наскільки алгоритм оптимальний?                     | Це детермінований жадібний розподіл із явними обмеженнями й залишком; доказу глобального оптимуму або ефективності навчання немає.                                                  |
| Чи готово до production?                            | Перевірено ядро локальної інтеграції й CI. Реальні TLS/proxy/cookie/scheduler/deployment перевірки не завершені.                                                                    |

## Що переглянути перед репетицією

Уточнити офіційну назву/академічне ТЗ, вимоги кафедри й час. Перевірити доступність підготовленого середовища та публічні матеріали, а не запускати повторно весь acceptance harness. Зіставити календарні дати з датою виступу, перевірити дозволи на нові fixtures, підготувати читання збережених результатів і три діаграми: система, планування, AI-confirmation. Формулювання про тести мають відповідати [доказам](testing-and-results.md), включно з зафіксованими backend deprecation/notices.
