# Актуальність оглядів: перевірка

2026-11-14. Перед змінами перевірено git status --short обох
репозиторіїв: чисті дерева, main. Простежено listing/annotate,
PlanningAttentionStatusService, Dashboard, planningAttention, RecoverySuggestions.
Автоматизовані тести не додавалися, не редагувалися та не запускалися.

## Підтверджені дефекти до змін

- Після зміни уподобань attention-status повернув check_pending=true й нуль
  актуальних пропозицій, але pending listing мав total=1 із рядком
  status=invalidated. Перевірка annotate виконувалася після paginate/count.
- Dashboard використовував довжину свого одноразово прочитаного списку, тому
  його заклик міг не відповідати поточному attention-status.
- Старий прямий GET повернув 200/status=invalidated і не дав червоної помилки.
  Точний текст зі згаданого скриншота «Не вдалося виконати дію» не відтворено.
- Натомість відтворено конкретну червону помилку після «Нового огляду»:
  POST `/api/planning/recovery-suggestions/{id}/refresh` повернув 409 із
  code=no_recovery_needed та message «Зараз рекомендація з відновлення не потрібна.».
  ApiError замінив не внесений до каталогу текст загальним конфліктом:
  «Не вдалося застосувати зміну через конфлікт. Перевірте поточні дані.».
  RecoverySuggestionsView помилково записував його в actionError/uncertain.
  Це очікуваний результат refresh, а не збій прямого читання старої картки.

## Зміни Backend та висновки з коду

- listing pending бере кандидатів через unique active_owner_id і status, викликає
  той самий annotate, що й індикатор, потім обмежує SQL за поточними ID до
  paginate. Тому stale/expired не впливають на сторінку/total. Немає повного
  читання історії; CHECK та unique обмежують кандидатів одним на власника.
- GET лишився read-only: немає analysis/store/resolve/lockForUpdate на читанні.
  Не змінено receipt, token, review, owner-first locks детектора й confirm.
  «Усі» як і раніше читає лише свою сторінку історії та анотує її.
- Якщо завершена перевірка має старий активний огляд, індикатор просить явне
  оновлення замість удаваного pending job. Dirty/running/failed зберегли семантику.
- Explicit refresh із kind=null під наявним owner lock викликає штатний
  recordScan(no_need) й лишає 409/no_recovery_needed. Як при detect, це завершує
  scan version/lease; старі jobs не породжують нових аналізів за тим самим token,
  наступний source writer позначить стан dirty. Конкурентний перебір усіх
  перестановок jobs вручну не проводився; взаємодію перевірено за кодом.
- Алгоритм allocation, правила ручного відновлення та server consent не змінено.

## Зміни Frontend та висновки з коду

- Dashboard читає planningAttention, а не довжину окремого cached feed; має
  checking/current/refresh-required і перечитує індикатор при вході.
- RecoverySuggestions слухає звичайні оновлення attention в цій вкладці й
  повторює тільки GET. Зберігає відкриту картку, переносить її до історичної
  групи, не зараховує її як pending. Read errors зберігають власний retry.
- Історичні заголовки/описи відрізняються від поточних вимог. Старий replan
  позначений «Історичний огляд», а не «Ще не збережено». AI-компоненти й чат
  не змінювалися; optional historical у ReplanningReport за замовчуванням false.
- no_recovery_needed зіставляється лише за ApiError.code в explicit refresh,
  не за будь-яким 409 чи перекладом. Після нього виконуються тільки GET списку,
  status і старої картки. Автоматичного повтору refresh/confirm немає.
