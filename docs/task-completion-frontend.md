# Завдання та спільне завершення роботи: Frontend

## Локальні репозиторії й межі

Frontend: поточний репозиторій `student-planner-frontend`, гілка `main`.
Backend знайдено поруч під назвою `../student-planner-backend`; корінь підтверджено командою `git -C ../student-planner-backend rev-parse --show-toplevel`.

Прочитано обидва `AGENTS.md`, маршрути, список і деталі завдань, форму завершення сесії, `WorkCompletionService`, `StudySessionLifecycleService`, правила життєвого циклу, `TaskService`, запити валідації та наявні тести. Використано лише локальні копії. GitHub і повторне клонування не використовувалися.

Згідно з уточненням користувача реалізовано лише Frontend. Backend-файли не змінені; необхідні серверні зміни перелічено нижче. Робоча БД не використовувалася для перевірок із записом.

## Етап 1: дії та фільтр

- У картці активного завдання залишено основну кнопку «Завершити» та другорядну «Видалити». Видалення використовує наявний діалог підтвердження. Меню «Інші дії», позначення невиконаним і повернення до виконання прибрано зі списку.
- Для завершеного завдання показано «Переглянути» та «Видалити». Заголовок також веде до деталей. Правила DELETE і повторного відкриття через API не змінені.
- Перемикач «Активні / Завершені / Усі» за замовчуванням вибирає активні `pending` та `missed`. Оновлення списку після завершення чи видалення не скидає перемикач. Якщо остання сторінка спорожніла, список переходить на наявну сторінку.
- Завершений запис на прямому URL деталей відображається без форми редагування. Підзавдання такого запису також показуються без кнопок редагування. Активні завдання залишаються редагованими в деталях.
- Перед PATCH Frontend перечитує завдання. Якщо воно вже завершене, PATCH не надсилається, а сторінка переходить до подання лише для читання. Це UX-захист; він не замінює потрібної серверної заборони.

Чинний `GET /api/tasks` приймає лише один статус. Для «Активних» адаптер виконує два валідні запити: `status=pending` і `status=missed`. Для потрібної сторінки він дочитує достатні впорядковані частини обох списків (пакетами до 100 записів), об'єднує їх у порядку backend — дедлайн, порожній дедлайн наприкінці, ID — і лише потім виділяє сторінку по 15 записів. Загальна кількість — сума серверних total. Це не фільтрація вже завантаженої сторінки. `status=active` на сервер не надсилається; типи статусів API залишилися чинними.

Тест із 440 активними записами перевіряє восьму сторінку й дочитування після перших 100 записів. Для великих списків окремий серверний груповий фільтр був би ефективнішим і давав би одну узгоджену відповідь; його не додавали в цьому frontend-етапі.

## Етап 2: завершення роботи й сесії

Поточний контракт повторно використано. Нових endpoint або полів POST немає.

1. Кнопка «Завершити» відкриває огляд роботи. За замовчуванням вибрано завершення тільки роботи. Сесію користувач вибирає явно, навіть якщо кандидат лише один.
2. Наявний GET сесій вимагає період до 31 дня. Початково перевіряються останні 31 день; у діалозі можна вибрати інший період, зокрема старішу історію.
3. У виборі залишаються пов'язані сесії зі статусом `planned`, які вже почалися. Час у Frontend — попередня UX-перевірка; остаточний дозвіл перевіряє чинний серверний lifecycle. Для вибраної сесії додатково читається її `completion-review` та `can_complete_work`.
4. Показано назву роботи, дату, час і заплановану тривалість. Фактичні хвилини вводяться окремо; поле спочатку порожнє, запланована тривалість не підставляється.
5. Сесія підзавдання явно позначена: спільна дія завершує лише це підзавдання. Основне завдання не закривається цією дією.
6. Перед записом перечитуються завдання, вибране підзавдання та сесія. Виявлені зміни зупиняють POST і вимагають нового огляду. Підтвердження скасування інших майбутніх сесій використовує наявний серверний текст і токен.
7. Спільна дія надсилає рівно один `POST /api/study-sessions/{id}/complete` із `actual_minutes`, `complete_work: true` та `completion_token`. Окремий POST завершення завдання після цього не виконується.
8. Без вибраної сесії використовується чинний POST завершення завдання або підзавдання. Майбутні сесії скасовує Backend; вони не позначаються завершеними та не отримують фактичних хвилин.
9. Після невідомого результату чи конфлікту автоматичного повтору немає. Дія блокується до нового огляду; перевіряється також фактичний статус відповіді, перш ніж показати успіх.

Той самий діалог використано для завершення підзавдання з його картки. Поточний сценарій незалежного завершення сесії на сторінці сесії залишено без змін.

## Серверні зміни, потрібні окремим етапом

### Обов'язкова заборона редагування завершеного завдання

Чинний Backend **дозволяє** редагування завершеного завдання. Це підтверджено прямим PATCH у тимчасовій ізольованій MySQL: HTTP 200, зміна назви збережена при статусі `completed`.

Отже, критерій «завершене завдання не редагується через API» **ще не виконаний на сервері**. У цьому етапі реалізовано лише заборону в UI й перевірку перед PATCH.

Потрібна перевірка `TaskStatus::Completed` у `TaskService::update` після актуального читання під блокуванням власника/завдання та перед змінами, з відмовою 409. Не слід забороняти весь `TaskPolicy::update`: цей дозвіл також використовується наявними lifecycle-операціями, зокрема повторним відкриттям, правила яких мають залишитися чинними. Серверні feature-тести повинні покривати прямий PATCH/PUT, зміну статусу перед записом, відсутність побічних змін та збереження правил видалення/повторного відкриття.

### Атомарність і перевірка застарілого огляду

Наявний `StudySessionLifecycleService` уже виконує спільне завершення всередині транзакції з блокуваннями й викликає сервіси Task/Subtask. Невдала зміна сесії або застарілий набір майбутніх сесій відкочує також завершення роботи та скасування залежних сесій/нагадувань. Цю атомарність повторно використано, нової двокрокової операції немає.

Водночас поточний `completion_token` фіксує набір майбутніх сесій, а не повний знімок полів завдання та вибраної розпочатої сесії. Frontend виявляє зміни додатковим читанням, але не може закрити проміжок між цим GET і POST. Для гарантії відмови після **будь-якого** редагування оглянутих даних потрібна окрема серверна прив'язка токена до версії/знімка роботи та вибраної сесії з перевіркою під тими самими блокуваннями. Частковий запис двох операцій чинний атомарний контракт уже запобігає.

Серверної заборони, нової схеми токена, групового фільтра й нового API пошуку кандидатів у цьому етапі не впроваджували.

## Змінені файли Frontend

- `src/components/domain/TaskCard.vue` — компактні дії картки.
- `src/views/TasksView.vue` — перемикач, оновлення сторінок, відкриття огляду завершення.
- `src/views/TaskEditorView.vue` — завершені деталі лише для читання та перевірка перед PATCH.
- `src/components/domain/TaskSubtasks.vue` — подання лише для читання та огляд завершення підзавдання.
- `src/router/index.ts` — назва маршруту «Деталі завдання».
- `src/api/taskList.ts` — адаптер пагінації двох наявних статусів.
- `src/api/workCompletion.ts` — доступ до наявних review/complete для керованої форми, без зміни контракту.
- `src/composables/useWorkCompletion.ts` — завантаження огляду, явний вибір, перевірки й одноразовий запис.
- `src/components/domain/WorkCompletionDialog.vue` — форма завершення.
- `tests/task-actions-status.test.ts`, `tests/task-work-completion.test.ts`, `tests/helpers/workCompletionBackend.ts` — цільові перевірки й фікстура.
- `tests/ui.test.ts`, `tests/subtasks.test.ts`, `tests/planning.test.ts` — адаптація наявних сценаріїв до нового списку й явного підтвердження.
- `e2e/task-work-completion.spec.ts` — desktop/mobile сценарій завершення.
- `docs/task-completion-frontend.md` — цей звіт.

API-типи статусів та backend-файли у фінальному стані не змінені.
